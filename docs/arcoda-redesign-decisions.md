## 4. 音符レコード（第三層のデータ基盤）確定

### スキーマ
- **プリミティブ（音符ごと）**: 演奏ID・曲ID・順序index・小節/拍・調・テンポ・音価・音高・弦・ポジション・指・ミス種別(音程/タイミング/音色)・ズレ量(cents/ms)。
- **遷移（＝materialize・各音符レコードに焼き付ける／第一級データ）**: 音程(跳躍)・方向(上/下)・移弦(元弦→先弦)・ポジション移動(元ポジ→先ポジ・量)。
  - **格上げの理由（2026-07-03）**: 遷移こそがバイオリンのミス傾向の本質（移弦・ポジ移動・跳躍でミスが起きる）。
    都度導出ではなく解析時に計算して保持する。理由: 課題化のメイン軸／隣接再構築の不安定さ回避／推薦を直接フィールド照合で書ける。
  - **移動元の定義（確定）**: **直前の発音**（休符は透過し、最後に鳴った音を移動元とする）。**重音は遷移計算から無視**（遷移チェーンに参加させない）。
- 保存場所: 演奏ごとの分析JSON（既存 comparison_result.json の置き場）。DBには集計のみ。

### 現状（検証済 2026-07-03）
- per-note の pitch誤差(`pitch_cents_error`)・timing誤差(`start_diff_sec`)・弦(`string_id`)・指(`finger`)・
  ポジション推定(`_violin_position` `subtask_judges.py:422`)は**実装済み**。
- **未実装＝各音符への 調・テンポ・移動元/遷移 の付与**（＝実装①の対象）。

## 6. スコアリングは項目非依存（検証済・重要）

演奏マスターのスコアは既に音符レコード直集計で、55項目に依存しない。
- `pitchAccuracy = Σ(各音符 pitch_score) / total_notes`（`analyze_performance.py:1942-1954`）
- `timingAccuracy = start_ok な音符数 / total_notes`（:1952-1955）
- `bowingAccuracy` = 品質項目（§5、残す）から。
- `overallScore = (pitch + rhythm + bowing)/3` → マスター平均90。

→ **55項目を廃止してもスコアリング（マスター判定）は無傷**。項目が動かしていたのは課題化・推薦のみ。

## 7. 課題化・推薦モデル（案A＝属性ベース）確定

**軸カタログは作らない**（＝固定カテゴリの再導入を避ける）。音符が持つ全フィールドを使う。

- **グループ化＝全フィールドをマージナル（フィールド別に独立集計）**。フル属性一致は稀なので要求しない。
- **課題 ＝ あるフィールド値が「ミス率 ≥ 閾値 かつ 出現数 ≥ 最小サポート」**（sparsity対策）。
  - 集計範囲: ユーザーの演奏履歴を跨いで（傾向）＋直近演奏（即時）。
- **推薦（弱点練習）＝ そのフィールド値を多く含む教材**をランキング。
  - 既に練習済みの技術タグ・習得系特徴タグは、ミスは**記録するが弱点練習は出さない**（練習済みだから）。
- **深掘り**: 2フィールド組合せはサポートのある所だけ。調・テンポは単独課題化せず"修飾"に使う。
- グループ化キーに使うフィールド: 指は使う。**遷移（移弦・ポジ移動・跳躍・方向）は焼き付け済みの第一級キーで、課題化・推薦の主軸**。

### 遷移を主軸にした流れ（具体）
1. ①レコード: ミス音符に `移弦: A→E`・`ポジ移動: 1→3(量2)`・`跳躍: +7半音`・`方向: 上` を付与。
2. ②課題化: ミスを遷移でマージナル集計 → 「A→E移弦 4/6」「1→3ポジ移動 5/8」→ 最小サポート超で課題化。
3. ③推薦: 教材の音符列からも同じ遷移を計算し、**その遷移を多く含む教材**をランキングして弱点練習に出す。

### 第三層の2つの仕事
- (A) ミス傾向の記録・可視化 → 全項目（技術・特徴タグと重複する項目も記録）
- (B) 弱点練習の推薦 → 未練習の項目のみ（練習済みの技術・習得系特徴タグは除外）

## 11. fingering 運用方針と弦/ポジ推定（工程0-① 2026-07-03 確定）

### 実測結果
- **教材に fingering は0件**（arpeggio/bowing/double_stop/fingering/scale で実測確定。etudeは.mxl圧縮で未確認）。
- 「fingeringカテゴリ」ですら fingering記譜0。XML形式が混在（etudeのみ.mxl圧縮、他はplain）。etudeに同一bytes重複の疑い。

### fingering 運用方針（確定）
- **全音符には入れない**。基本ルール:
  - **記載なし ＝ 1stポジションで押さえる音** → 弦・ポジは音高から推定（1stポジ前提）。
  - **1stポジ以外の音 ＝ 指番号(1〜4)だけを記載** → 指番号＋音高から「弦・ポジション」を推定する。弦番号・ポジション番号は入れない。
- 既存教材（fingering0件）は全部「1stポジ」とみなす。高ポジを使う既存教材は後から指番号をbackfillする運用。

### 弦/ポジ推定ロジック（指番号＋音高 → 弦・ポジ）
- 手順: ①弾ける弦候補を絞る（音高<開放弦は除外）→ ②各候補弦でポジション逆算（音高−開放弦−指オフセット）→ ③前後音との連続性（手の移動最小・移動元=直前の発音）で確定。
- 完全一意でない少数はヒューリスティックで吸収。

### 現行実装との差分（実装①で対応）
- 現行 `lib/violin_position.py` は「フォールバック専用の1stポジ推定」で、あなたの方針と設計思想一致・**1stポジ側は実装済**（VIOLIN_FIRST_POSITION_MAP, MIDI 55-83）。
- **差分1**: 「指番号→弦・ポジ導出」経路が無い（現行は明示 `<string>` 前提の `string_num_to_id`）。→ **新規実装**。
- **差分2（重要な穴）**: 現行は **MIDI 84+(C6以上)を string_id=None＝移弦判定の対象外**に落とす（コメント: 既存mxlの86%がMIDI84+を含む）。fingering無しの現状、**高音は弦/ポジ/遷移の分析から丸ごと欠落**。→ 方針転換で高音に指番号が付けば解決するが、既存教材はbackfillまで欠落のまま。**上限撤廃が実装①の対象**。

## 12. 技術タグ自動抽出（工程0-② 2026-07-03 現状把握）

### 現状（実測）
`analyze_musicxml.py` は **music21 経由で13技術タグの大半を既に抽出済み**。ゼロからではない。
- 明示フラグ: is_tremolo(弓/指・刻み数)・is_trill・is_harmonic(natural/artificial)・is_glissando(音程差/方向)、spanners.slurs。
- articulation_list（music21型名）: Staccato / Spiccato / Pizzicato / DetachedLegato 等。
- モルデント: 記号あり(`<ornaments><mordent/>`/`<inverted-mordent/>`, music21 expressions.Mordent/InvertedMordent)。現行 expressions ループが Tremolo/Trill しか見ていないだけで**追加は1行レベルで自明**。→ 13技術タグは全て抽出可能（ビブラートのみ意図的除外）。

## 14. 特徴タグ スキーマ確定（工程0-③ 2026-07-03）

**範囲＝案Y：初版で全特徴タグを作る**（重音・数値だけに絞らず、rhythm7要素・dynamics も含む）。一貫性優先、後からの動的拡張の手間を避ける。

### 数値系カラム（Score / PracticeItem に追加）
- keys[]（複数調・主調先頭。keyTonic/keyMode は主調で維持）
- pitchMin / pitchMax（MIDI）
- positions[]（Score は新設。PracticeItem 既存 String[] → **Int[] に揃える方針**、移行は実装指示書で）

### リスト系：FeatureTag テーブル＋中間テーブル（ScoreFeatureTag / PracticeItemFeatureTag、TechniqueTag と同型）
```prisma
model FeatureTag {
  id            String  @id @default(cuid())
  category      String  // "rhythm" | "double_stop" | "dynamics"
  name          String
  extractRule   String? // 抽出条件メモ（動的拡張§23用）
  isAcquisition Boolean @default(false) // 習得系(重音)=true → 達成をゲート
  scores        ScoreFeatureTag[]
  practiceItems PracticeItemFeatureTag[]
  @@unique([category, name])
}
```
- FeatureTag 初期データ（全カテゴリ）:
  - rhythm: 8分/16分/32分 / 付点 / 休符(拍頭・裏拍) / 連符(3連符) / 装飾音符 / シンコペーション
  - double_stop（isAcquisition=true）: 3度/6度/8度/10度… / 連続重音
  - dynamics: クレッシェンド等
- 抽出配線: rhythm は MusicXML type/dot/rest/time-modification/grace/tie から、double_stop は chord＋音程計算、dynamics は wedge/dynamics から。

### 承認ゲート
- 上記スキーマ変更（数値カラム＋FeatureTag＋中間テーブル）と analyze_musicxml 抽出追加は、すべて Prisma migration＝承認ゲート対象（実装指示書で承認フォーマットにかける）。

## 16. Star Progression 再吟味（残論点A2 2026-07-03確定）

- **★昇格＝「達成」ベース**（マスターではない）。**同★で10曲"達成"したら次の★へ昇格**。
- 理由: 達成＝「そのレベルの曲を通して弾ける」＝レベル到達の自然な signal。§3「達成＝次へ進む権利」と一致。モチベ優先でレベルが進む。
- **マスター（平均90）は★とは別軸の"完璧主義"アチーブメント**として並走（星に金メダル等）。★昇格の条件には使わない。
- ★は維持（ユーザーの現在難易度を定義し、難易度別教材クリア・事前練習・曲推薦の範囲を決める）。GradeLevel派生（1-3 BEGINNER/4-6 INTERMEDIATE/7-9 ADVANCED/10 MASTER）は現行流用。
- **実装差分**: 現行 loop_engine_runner の★昇格は isFullyMastered(≈マスター)をカウント → **「達成」カウントに変更**。UserGradeProgress.masteredSongCountAtCurrentStar の意味を"達成曲数"に。

## 17. 事前練習ロジック（残論点D1 2026-07-03確定）

### 事前練習＝曲を選んだ時に出す練習メニュー（達成に向けた準備）
1. 未習得の技術タグ・習得系特徴タグ → 学びレッスン（達成 a/c）
2. 各技術・習得系 → 難易度別教材クリア（達成 b/d）
3. **キーベース音階・アルペジオ**（達成 f・下記ロジック）＝**達成の必須要件**（案イ確定）
4. ポジション移動パターン教材（曲の positions[] とマッチ）

### 音階・アルペジオの選定ロジック（§21-1）
- **条件＝キー一致 ＋ 音域カバー（両方必須）**
  - キー一致: 主音＋モード完全一致（ト長調の曲→ト長調の音階）
  - 音域カバー: `音階.pitchMin ≤ 曲.pitchMin` かつ `音階.pitchMax ≥ 曲.pitchMax`
- **フォールバック**: 条件を満たす音階が無ければ、同一キーで最大音域の音階を代替提示
- **転調曲**: キー一致必須は主調のみ。副次調（調号変更で検出）の音階は「追加おすすめ」枠（必須外）
- アルペジオも同ロジック。
- **依存**: pitchMin/pitchMax（工程0-③の新設カラム）が前提 → 実装は特徴タグスキーマ後。

### 弱点練習側との対比（再掲）
- 事前練習＝曲選択時・特徴タグ（キー/音域/習得系）で選ぶ。
- 弱点練習＝演奏後・音符レコードの属性を集計して選ぶ（§7）。

## 18. 練習パターン・レジストリ（教材バリエーション生成の中核・2026-07-03設計）

### 概念
- **教材 ＝ ベース教材 × パターン**。ベース教材（エチュード/音階/アルペジオ/毎日の練習フレーズ）の pitch・弦・ポジションは不変のまま、**弾き方（奏法・リズム）だけをパターンで上書き**して variant を生成。
- **パターン・レジストリは全大区分で共通**（1つのテーブルを音階・アルペジオ・エチュード・毎日の練習すべてに適用）。
- パターンを掛けると、そのパターンの**誘発タグ**（既存の技術タグ・特徴タグ）が自動で付く。パターン＝生成側、タグ＝分類側で対応。

### パターンの2タイプ
**① 単一パターン（1音・均一）** — 全音符に同じ弾き方
- 全デタシェ / 全スタッカート / 全スピッカート / 全マルテレ(→スタッカート) / 全トレモロ / 全16分 / 全8分 / 全32分

**② グループパターン（繰り返しテンプレート）** — 各位置に「リズム値＋奏法の役割」を並べた単位を循環適用
- 例: 2音スラー=[スラー始,スラー終] / 1単独+3スラー=[単独,スラー始,スラー中,スラー終] / 付点=[付点長,短] / 8分+16分16分=[8分,16分,16分] / 4スラー+4スタッカート / ボウ・スタッカート / ポルタート / リコシェ / 三連符 / シンコペーション
- **誘発タグ ＝ テンプレートに含まれる役割の合算**（例 8分+16分16分 → 8分＋16分）。

### 拡張性（仕様の中核・Tetsuo 強調 2026-07-03）
- **パターンは今後 増える・減る 前提**。100点のパターン集を今作る必要はない。改良を継続する。
- レジストリ（テーブル）で管理: {id, 名前, タイプ(単一/グループ), テンプレート(グループ時), 誘発タグ, 適用先, 変換ルール}。
- **パターン追加時**: 既存の全ベース教材に自動適用 → variant 再生成 → 誘発タグ自動付与 → カバレッジ行列に自動反映（§23の動的タグ拡張と同一機構）。
- **パターン削除・改訂時**も同機構で再生成。
- カバレッジは**マージナル**（誘発タグ別に「★Nで1つでもあるか」。組合せは作らない）。1つの variant が複数タグのセルを同時に埋める＝生成の梃子。

## 19. 動的タグ拡張の仕組み（残論点D4 2026-07-04確定・§4-4/§23を新設計と統合）

「後から足すと既存に自動で行き渡る」仕組み。設計フェーズの最後のピース。

### 動的に追加できるもの
- **リスト系タグ（TechniqueTag / FeatureTag）＋ パターン（§18レジストリ）**。
- ✗ 数値系カラム（pitchMin/max・keys[]・positions[]）＝スキーマ変更なので承認ゲート経由の通常開発。

### 再生成の2経路
| 追加 | 再生成 | 対象層 |
|---|---|---|
| タグ（技術/特徴） | analyze_musicxml 再実行 → 全曲/教材を再タグ付け | 静的タグ（達成要件・表示・事前練習） |
| パターン（§18） | pattern_generator 再実行 → 全ベース教材に新variant生成＋誘発タグ付与 | 教材生成層（カバレッジ充足） |

### 確定ルール
- **遡及なし**: 既に確定した達成・マスター・Starは取り消さない（永続ロック）。新タグ/パターンは付与以後の判定・生成のみに適用。過去のユーザー進捗を壊さない。
- **要確認キュー**: 曖昧記号（スタッカート系§18-2）絡みの新タグは自動確定せず「要確認リスト」に積む→管理者が後日回答。
- **サイレント更新**: ユーザー通知不要・再アップロード不要のバッチ処理。
- **カバレッジ行列 自動再集計**: 拡張後に穴を再可視化。
- **パターン削除・改訂時**: 生成済みvariantは**論理削除**（ユーザーから見えなくする・推薦に出ない・カウントしないが、DBレコードは残す＝過去の練習履歴・達成記録を保護。deletedAt/isPublished で実装）。完全削除はしない。
- **音符レコードの新フィールド追加時**も遡及なし（過去演奏は再分析せず、以後の演奏のみ）で統一。
- **難易度別教材クリアとの区別**: 学びレッスン＝「全体で最簡・一度・永続（触れたことがある）」／難易度別教材クリア＝「今の難易度の教材・各難易度で（そのレベルで使える）」。
- 対象: 全13技術タグ＋習得系特徴タグ（ポジション番号ごと・重音音程種別ごと）。UIフロー[1]がこれを流す。
