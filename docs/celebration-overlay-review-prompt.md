## 前提：あなたはコードベースを見られない
設計書は下記「著者が実コードから確認したと主張する事実（=前提）」に依拠しています。
あなたはコードを直接検証できないため、これらは「真偽が設計を左右する“検証すべき主張”」
として扱い、もし誤っていたらどこが崩れるかを必ず明示してください。

### 著者が主張する前提（load-bearing facts）
1. 解析は非同期(queued→processing→done)。フロントは曲/教材の詳細画面が3秒ごとにポーリングして完了を検知する（`scoreDetail.tsx` の polling useEffect / 完了検知 useEffect）。長い曲/コールドスタート/OOMで数秒〜分かかり得る。
2. 解析時のPython `lib/achievement.py: process_score_achievement` が `{achieved, mastered, star_up}` を返し、同時に `UserScoreAchievement(achievedPerformanceId)`, `masteredAt`, `UserStarProgress.currentStar` を永続化する（達成/マスター/ランクアップの判定は既存）。
3. ただしその戻り値は今 `loop_engine_runner.py: _run_achievement_v2` で `print` されるだけで、フロントが読める場所(`Performance.analysisSummary`)には保存されていない。一方で診断は `save_performance_diagnosis` で `analysisSummary` にマージ保存済み＝同じ経路で `milestone` も保存できる、というのが設計の中核。
4. 「今録音した演奏の完了」を1回だけ検知する既存の仕組みがある（`scoreDetail.tsx` の `justRecordedRef` + `sessionStorage("arcoPending")`、発火時に自己クリア）。
5. `UserPracticeMastery` は「直近5回平均≥90 かつ累計≥5・`masteredAt`固定・不可逆」の定義でスキーマに存在するが、現行パイプラインは書いていない。設計はこれを“再利用”してデータを書くだけ（スキーマ変更なし）で「教材クリア=直近5回平均90」を検知する。
6. 現行の `process_practice_achievement` は別定義(3回崩壊ゼロ=`UserPracticeAchievement`)。よって「教材クリア(直近5回平均90)」は新規判定ロジックの追加が必要。
7. マスコット `ArcoChan` は30ポーズ＋CSSアニメ(hop/clap等)実装済み。録音直後オーバーレイ `ArcoResultOverlay` は既存(曲のみ)。共有/OG画像/公開リンクのインフラは存在しない。`MyRankCard` が達成スタンプを表示済み（本棚の素地）。
8. achievement判定は SAVEPOINT 隔離で失敗を握り潰す設計(解析本体を壊さない)。
9. 定数: `CLEAN_RUNS_REQUIRED=3` / `MASTER_RECENT=5` / `MASTER_AVG=90` / `STAR_UP_ACHIEVEMENTS=10`。
10. Cloud Run(Python)は手動再デプロイ必須。Prisma本番マイグレーションは手動運用。

## この設計が満たすと主張している要件（ここが本当に守られているかを重点検証）
- **A. 単一リリースで完結し、イメージと違えば即ロールバックできる**
  （スキーマ変更ゼロ／全変更は加算のみ／単一フラグ `CELEBRATION_ENABLED` でゲート／フラグOFF=現状と完全一致／L1ロールバック=フラグOFFのみ）
- **B. 拡張性・横展開**：祝いの「種類(type)」「発生源(source)」「タイミング」「配信先」をそれぞれ独立に“足すだけ”で増やせる（4層分離＋2つのレジストリ＋`dedupeKey`で1回性）

## レビュー観点（最低限すべて評価）
1. 内部整合性・正確性（前提1〜10と設計の主張が噛み合っているか）
2. フィージビリティ（Python/フロント/デプロイ運用で本当に実現可能か）
3. 「フラグOFF=現状と完全一致」は本当か（分岐の抜け、副作用、ビルド/型影響）
4. ゼロ・マイグレーションの主張は妥当か（既存テーブル再利用の落とし穴、`UserPracticeMastery` を“書き始める”ことの副作用・整合性リスク）
5. 冪等性・1回性（既存トリガー再利用で十分か。二重発火・遡及祝い・多端末・StrictMode二重実行・リロード/背面復帰の穴）
6. 「教材クリア=直近5回平均90」の定義一貫性（推薦ロジック等 他所の定義との齟齬、境界条件: 4回目/5回目/既クリア/区間録音の扱い）
7. 拡張性の主張の検証（type/source/timing/deliveryの分離は本当に結合を生まないか。`selectCelebrations`/レジストリ/エミッタ/キューの境界に破れはないか。`dedupeKey`設計の穴）
8. エッジケース（解析遅延中の離脱、解析失敗、同時多節目の重なり、自己ベスト吸収、`prefers-reduced-motion`、区間録音除外）
9. セキュリティ/プライバシー（Web Share、音声非含、外部送信、記念カードに含める情報）
10. 運用・テスト（Cloud Run手動デプロイ、リリース手順、pytest/Vitestの十分性）
11. 見落とし・未記載のリスク、より良い代替案
